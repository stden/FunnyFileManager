# 3. I/O, потоки и производительность

В TUI пользователь ожидает, что нажатия и перерисовка работают, пока сервер
отвечает. Сетевой запрос внутри рендера блокирует весь интерфейс.
Даже быстрый запрос становится проблемой при повторении на каждом кадре.

## Разделите решение и эффект

В FFM путь действия проходит через несколько владельцев:

```text
клавиша → типизированная команда → операция → состояние → рендер
                                      ↓
                                 фоновый worker
                                      ↓
                              результат → состояние
```

Обработчик клавиш решает, что попросить. Операция создаёт запрос.
Адаптер выполняет I/O. Рендер читает уже готовое состояние.
Смотрите [remote_jobs](../../../src/application/remote_jobs.rs) и
[операции удалённой панели](../../../src/ops/remote.rs).

Для обычного приложения можно выбрать потоки или async runtime.
В FFM сначала используйте существующий механизм фоновых работ.
Добавление второго runtime требует причины: async сам по себе не делает
блокирующий DNS-запрос или файловую операцию неблокирующими.

## Поздний ответ может стать неправильным

Пока загружался каталог, пользователь мог открыть другое подключение.
Успешный результат старого запроса не должен вернуть его в старую панель.
Свяжите запрос с идентификатором поколения или объекта, а при публикации
проверьте, что целевой экран ещё тот же.

Для редактора проверяйте также ревизию: если во время сохранения появились новые
правки, завершение старого сохранения обновляет базовую версию файла, но оставляет
документ изменённым. Иначе UI сообщит, что несохранённых изменений нет.

## Ограничивайте ресурсы явно

Сетевой адаптер должен иметь таймаут, ограничение размера ответа и правило
обработки перенаправлений. Для постраничного API задайте общий предел работы
и обнаруживайте повтор курсора. Не выдавайте частичную сумму за полный отчёт.

Передавайте большие файлы потоком. Для редактора задайте отдельный разумный
предел размера. Запись во временный файл и последующее переименование полезны,
когда требуется сохранить исходный файл при неудаче.

Нельзя считать таймаут TCP полным ограничением операции: разрешение имени,
повторные запросы и несколько страниц тоже занимают время.

## Алгоритмическая сложность

Если на каждом кадре суммировать размеры всех файлов, стоимость кадра растёт
как O(n). Кэширование суммы делает повторное чтение O(1), но пересчёт остаётся
O(n) при изменении списка. Главное — правильно инвалидировать кэш.

| Задача | Подход | Цена и ограничение |
|---|---|---|
| Проверить членство в наборе | HashSet | Ожидаемое O(1), дополнительная память |
| Сохранять сортированный порядок | BTreeMap | O(log n) для поиска и изменения |
| Найти префикс в отсортированном списке | Две бинарные границы | O(log n + k), где k — число результатов |
| Показать часть длинного списка | Видимое окно | Работа зависит от числа видимых строк |
| Обработать дерево каталогов | Явный стек | Память для очереди, управляемая глубина |

HashSet нельзя использовать как источник стабильного порядка для UI.
При одинаковом результате тест должен получать одинаковую последовательность.
Для DFS учитывайте циклы и символические ссылки; список имён сервера — недоверенные
данные, а не готовые локальные пути.

## Измеряйте вместе с проверкой корректности

Сначала получите исходное время, затем меняйте реализацию.
Используйте одинаковую сборку, входы и условия. Разделяйте холодный и прогретый
кэш, измеряйте несколько размеров данных. Маленький синтетический пример
не доказывает ускорение полного кадра.

Для Rust в FFM есть `benches/` и Criterion. Результат описывайте вместе с
условиями измерения и ценой в памяти. Не повышайте пороги Clippy ради ускорения.

## Упражнение

Реализуйте обновление списка через тестовый worker. Закройте панель до прихода
ответа и проверьте, что она не открылась заново. Затем измерьте повторную
перерисовку списка из 1 000 и 100 000 элементов.

Критерий: устаревший ответ безопасен, а выводы о скорости опираются на измерения.
