# 4. Тесты и рабочий процесс

Хороший тест описывает наблюдаемое поведение. Для файлового менеджера это
содержимое файла, выбранная строка, сообщение об ошибке или текст на экране.
Проверка последовательности внутренних вызовов часто делает рефакторинг дорогим,
не доказывая, что пользователь получил правильный результат.

## Цикл TDD

1. Выберите одно поведение и подготовьте минимальную фикстуру.
2. Напишите тест и убедитесь, что он падает по нужной причине.
3. Реализуйте минимальное законченное поведение.
4. Запустите тест, затем уберите повторения и проясните имена.
5. Проверьте соседние сценарии и полный обязательный набор перед коммитом.

Для дефекта сначала воспроизведите его отдельным тестом.
Успешный тест, который никогда не видел ошибочную реализацию, может проверять
совсем другую ветку.

## Изолируйте файловую систему

```rust
#[test]
fn failed_copy_keeps_the_existing_destination() -> std::io::Result<()> {
    let temp = tempfile::TempDir::new()?;
    let destination = temp.path().join("document.txt");
    std::fs::write(&destination, b"original")?;
    let result = std::fs::OpenOptions::new()
        .create_new(true)
        .write(true)
        .open(&destination);
    assert!(result.is_err());
    assert_eq!(std::fs::read(&destination)?, b"original");
    Ok(())
}
```

Это самостоятельный пример проверки гарантии `create_new`.
Для проверки FFM вызывайте операцию приложения и проверяйте результат тем же
способом. Не ограничивайтесь повторением реализации в тесте.

Тесты не должны читать домашний каталог, менять глобальный текущий каталог,
подключаться к рабочему серверу или удалять настоящие файлы пользователя.
Используйте `TempDir`, инъекцию транспорта и явные снимки панелей.

## Тестируйте границы, где теряются данные

| Сценарий | Что проверить |
|---|---|
| Ошибка чтения конфига | Исходник не перезаписан пустым документом |
| Одновременное сохранение | Конфликт обнаружен, чужой раздел сохранён |
| Обрыв загрузки | Исходный файл и источник перемещения сохранены |
| Недоверенное имя | `..` и абсолютный путь не выходят за целевой каталог |
| Поздний ответ | Закрытая панель не открывается заново |
| Секрет в форме | Нет секрета в рендере, истории и сообщении об ошибке |
| Пагинация статистики | Все страницы учтены один раз, сбой не выглядит нулём |

Для транспорта полезны два уровня: быстрый fake для сценариев приложения
и локальный протокольный сервер для проверки реального адаптера.
Не называйте проверку fake-транспорта проверкой совместимости с настоящим SSH.

## Тесты TUI

Создайте `ratatui::backend::TestBackend`, нарисуйте состояние и проверьте буфер.
Для маски пароля проверяйте не только наличие звёздочек, но и отсутствие
исходного секрета. Для выбора строки проверьте стиль, если именно он обозначает
выбор. Клавиатуру и мышь направляйте в один канонический обработчик операции.

## Организация кода

В FFM модуль `foo` находится в `foo.rs`, а дочерние модули — в `foo/`.
Тесты размещаются в отдельных `tests.rs` или `tests/`.
У каждого файла есть строка `Purpose`. Функции и файлы ограничены по размеру;
разделяйте их по ответственности, а не ради механического сокращения строк.
Внутренний интерфейс по умолчанию имеет видимость `pub(crate)`.

## Перед коммитом

Из корня репозитория:

```text
cargo fmt
python ffm.py lint
cargo test
```

Дополнительные проверки выбирайте по изменению: `cargo test --features test-helpers`,
нужные пакеты MCP/Colorer, бенчмарки для производительности.
`python ffm.py coverage` запускайте при работе над покрытием: сохранённые
артефакты `coverage/` не обновляются при обычной правке.

Общий lint проверяет форматирование, орфографию, ограничения сложности,
дублирование, Clippy и архитектурные контракты.
Не отключайте предупреждение вместо исправления причины.

## Итоговая работа

Создайте панель статистики тестового провайдера:

- Состояние загрузки задаётся enum, число токенов — newtype.
- Ключ не сериализуется и не имеет `Debug`.
- API вызывается в фоне с ограничениями ресурсов.
- Обрабатываются пустой ответ, отказ доступа и несколько страниц.
- Поздний ответ не меняет новый экран.
- Сохраняется только пользовательская конфигурация, остальные YAML-разделы остаются.

Критерий готовности: тесты описывают эти гарантии, интерфейс остаётся отзывчивым,
обязательные проверки проходят, изменения закоммичены и отправлены.
